# TDD на Python: разработка через тесты

## Зачем нужен подход

TDD — Test-Driven Development — организует работу короткими циклами: **Red → Green → Refactor**. Сначала тест нового поведения падает, затем появляется реализация, затем улучшается структура без изменения поведения.

Тест до реализации заставляет определить интерфейс и ожидаемый результат. Сам по себе порядок написания не гарантирует качества: неверное требование или слабое утверждение дадут неверный результат и при TDD.

Пример: лаборатория выдаёт оборудование. Нужно определить число дней текущей просрочки. Срок 12 апреля означает, что 12 апреля просрочки нет, 13 апреля — один день. Для возвращённой выдачи текущая просрочка равна нулю; историческую длительность задержки эта функция не считает.

Материал автономный. Python 3.11+, только стандартная библиотека `unittest`. Названия файлов ниже нужно сохранить буквально. `unittest` выбран, чтобы пример запускался без установки пакетов; тот же процесс применим с pytest.

## 1. Сначала контракт

Функция `overdue_days(due_on, today, returned=False)` получает две даты и признак возврата, возвращает неотрицательное целое число. Даты передаём явно: тесты не должны зависеть от реальных часов.

Список поведения, которое будем добавлять:

1. До срока — ноль.
2. В день срока — ноль.
3. После срока — число прошедших календарных дней.
4. После возврата — ноль независимо от прежней задержки.

Внешняя проверка строковых дат в этот контракт не входит: функция принимает объекты `date`.

## 2. Первый Red

Создайте модуль `loan_rules.py` с заглушкой:

```python
def overdue_days(due_on, today, returned=False):
    raise NotImplementedError
```

Создайте `test_loan_rules.py`. Пока оставьте только первый тест из полного файла ниже — `test_before_due_date`. Запустите:

```bash
python -m unittest -v test_loan_rules
```

Ожидается ошибка `NotImplementedError` в тестируемой функции. Это первая красная проверка отсутствующего поведения. Ошибка импорта или отсутствие Python не подтверждают проверку бизнес-правила.

## 3. Первый Green

Замените тело функции на `return 0`. Один тест должен пройти. Такая реализация пока недостаточна для всей задачи, но соответствует текущему проверяемому шагу. Не останавливайтесь на ней.

Добавьте `test_on_due_date`: он пройдёт сразу, поскольку текущее решение уже покрывает этот случай. Не нужно искусственно ломать код, чтобы каждый новый тест был красным.

Добавьте `test_after_due_date`: теперь `return 0` неверен, тест должен упасть. Реализуйте вычисление разности дат с нижней границей ноль. Старые тесты должны остаться зелёными.

Добавьте `test_returned_loan_is_not_currently_overdue`. Он выявит отсутствие обработки возврата. Допишите правило и снова запустите весь набор.

## 4. Итоговые файлы

Это конечное состояние после описанных циклов. Чтобы выполнить упражнение, сначала пройдите последовательность, а не копируйте весь результат сразу.

### Файл `loan_rules.py`

```python
from datetime import date


def overdue_days(due_on: date, today: date, returned: bool = False) -> int:
    if returned:
        return 0
    return max(0, (today - due_on).days)
```

### Файл `test_loan_rules.py`

```python
from datetime import date
import unittest

from loan_rules import overdue_days


class OverdueDaysTests(unittest.TestCase):
    def test_before_due_date(self):
        self.assertEqual(
            overdue_days(date(2030, 4, 12), date(2030, 4, 10)), 0
        )

    def test_on_due_date(self):
        self.assertEqual(
            overdue_days(date(2030, 4, 12), date(2030, 4, 12)), 0
        )

    def test_after_due_date(self):
        self.assertEqual(
            overdue_days(date(2030, 4, 12), date(2030, 4, 15)), 3
        )

    def test_returned_loan_is_not_currently_overdue(self):
        self.assertEqual(
            overdue_days(date(2030, 4, 12), date(2030, 4, 15), returned=True),
            0,
        )

    def test_crosses_month_boundary(self):
        self.assertEqual(
            overdue_days(date(2030, 4, 30), date(2030, 5, 2)), 2
        )


if __name__ == '__main__':
    unittest.main()
```

После добавления последнего теста ожидается `Ran 5 tests` и `OK`. Количество секунд зависит от среды.

## 5. Что делать на Refactor

Проверьте имена, дублирование, зависимости и ясность контракта. Например, первоначальные вложенные `if` можно заменить коротким `max`, сохранив тесты зелёными. Не нужно создавать классы, если одна функция выражает правило достаточно хорошо.

Если улучшать нечего, допустимо оставить код как есть. Refactor — осмысленная проверка структуры, а не обязательная механическая правка после каждого теста.

## 6. Как проверить полезность тестов

Временно внесите по одной ошибке и запускайте набор:

| Ошибка | Что должно её обнаружить |
| --- | --- |
| Всегда возвращать ноль | Проверка просрочки |
| Убрать ограничение снизу | Проверка даты до срока |
| Убрать обработку `returned` | Проверка возвращённой выдачи |
| Вычитать номера дней месяца | Проверка перехода через месяц |

Восстановите правильный код. Не вычисляйте ожидаемое значение в тесте той же формулой, что используется в реализации: фиксированные примеры помогают не продублировать одну ошибку дважды.

## 7. Как работать с агентом

> Вот контракт и согласованные примеры. Реализуй правило короткими TDD-циклами. Сначала добавь тест нового поведения и фактически запусти его. Покажи причину падения. Затем исправь реализацию, запусти весь набор и оцени необходимость рефакторинга. Не меняй ожидаемые значения ради прохождения тестов.

Другому агенту поручите найти неверную реализацию, которую пропустят ваши тесты, и проверить соответствие контракту. Человек решает, достаточно ли самого контракта: возможно, заказчику вообще нужен исторический отчёт, а не текущая просрочка.

## 8. Самостоятельная работа

Добавьте `can_issue(active_count, limit, has_overdue)`:

- `active_count` — целое число не меньше нуля; `limit` — положительное целое;
- при просрочке выдавать нельзя;
- при `active_count >= limit` выдавать нельзя;
- иначе можно;
- некорректные числовые значения вызывают `ValueError`.

Начните со списка примеров, затем выполняйте циклы по одному правилу. Явно решите, принимаете ли `bool` как целое число: в Python это подтип `int`. Сдайте тесты, реализацию и один реальный Red–Green–Refactor.

## Где подход полезен и где его недостаточно

TDD удобен для правил, алгоритмов и регрессий. Он не заменяет обсуждение задачи, интеграционные проверки БД, ревью и тестирование конкурентного поведения. В исследовательском прототипе сначала допустимо выяснить, какой интерфейс нужен, а затем закрепить выбранный контракт тестами.
