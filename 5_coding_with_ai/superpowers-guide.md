# Разработка с Superpowers: обзор и учебный практикум

Материал для студентов ИТ-направлений и разработчиков, знакомых с Git, Python и основами автоматического тестирования.

**Разбираемый проект:** [obra/superpowers](https://github.com/obra/superpowers), автор Jesse Vincent, лицензия MIT.

**Основа материала:** исходники с версией `7.0.0` в манифесте, commit `b739a8af570e10a95898f2bdf6cec97467fa6c12`, проверенные 21 октября 2026 года. Команды установки и детали поведения относятся к этому срезу. Ветка `main` меняется; для воспроизводимого занятия фиксируйте версии плагина и агента.


## 1. Что такое Superpowers

Superpowers — набор связанных skills и интеграций, который задаёт coding-агенту процесс разработки. Он помогает провести задачу через уточнение требований, планирование, реализацию, тестирование, ревью и завершение ветки.

Сам агент уже умеет читать файлы, менять код, запускать команды и иногда создавать субагентов. Superpowers объясняет, **когда и в каком порядке применять эти возможности, что проверять и какой результат оставлять после каждого этапа**.

Например, на просьбу «добавь экспорт заказов в CSV» агент должен сначала разобраться в составе выгрузки и ограничениях, затем составить план, реализовать поведение через тесты, организовать ревью изменений и предъявить результаты проверки.

| Компонент | Его роль |
|---|---|
| Модель | Понимает запрос, предлагает решения, пишет код |
| Агентная среда: Claude Code, Cursor, OpenCode и другие | Предоставляет инструменты, доступ к проекту, сессии и разрешения |
| Superpowers | Задаёт инженерный процесс через skills, шаблоны и интеграции |
| Репозиторий проекта | Хранит код, тесты, спецификации, планы и историю изменений |
| Разработчик | Определяет нужный результат, проверяет решения, принимает изменения |

Superpowers не обучает модель заново, не является отдельной LLM и не заменяет агентную среду. Его основной механизм — инструкции в контексте модели. Это также не MCP-сервер: MCP обычно подключает инструменты и данные, а Superpowers организует работу с уже доступными возможностями.

**Установка не доказывает соблюдение процесса.** Агент может неправильно выбрать skill, пропустить проверку или ошибиться в требованиях. Оценивать нужно действия, diff и результаты команд.

## 2. Из чего он состоит

В репозитории есть несколько групп компонентов:

| Часть | Что находится внутри |
|---|---|
| `skills/` | Каталоги skills с `SKILL.md`, дополнительными инструкциями и примерами |
| Шаблоны внутри skills | Задания исполнителю и ревьюеру, правила отчётности и повторной проверки |
| Скрипты внутри skills | Подготовка brief задачи, пакета diff для ревью и рабочего каталога плана |
| `hooks/` | Подключение стартовых инструкций к событиям агентной среды |
| Манифесты и адаптеры платформ | Регистрация плагина и согласование с инструментами конкретного агента |
| `tests/` | Проверки самого Superpowers |

Типичный `SKILL.md` содержит имя, описание условий применения и инструкцию работы. Дополнительные файлы загружаются по необходимости. Весь репозиторий не требуется постоянно держать в контексте.

Стартовый skill `using-superpowers` требует проверять применимость skills перед действиями. В Claude Code стартовая интеграция использует событие `SessionStart`, в том числе для восстановления инструкций после compaction. У других платформ механизм отличается.

Это важное различие между **просто папкой с полезными промптами** и интегрированным плагином: плагин помогает агенту обнаружить инструкции и включить их в рабочий процесс. Но текстовое требование «обязательно запускай тесты» всё равно не равно техническому запрету завершать работу без тестов. Для жёсткого контроля нужны отдельные механизмы: CI, обязательные проверки PR, ограничения разрешений.

## 3. Установка и проверка

Выберите одну среду. Установка в один агент не означает установку во все остальные.

### Claude Code

Команда выполняется в интерфейсе Claude Code:

```text
/plugin install superpowers@claude-plugins-official
```

Альтернативный источник — marketplace проекта:

```text
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace
```

Это два альтернативных пути установки одного плагина. Для занятия достаточно одного.

### Cursor

В чате Cursor Agent:

```text
/add-plugin superpowers
```

Также можно найти Superpowers в marketplace плагинов. Речь идёт о плагине агентного режима; установленный плагин не означает, что каждое обычное автодополнение кода будет проходить полный процесс разработки.

### OpenCode

В документации проекта различаются конфигурации OpenCode V1 и V2.

Для V1:

```json
{
  "plugin": ["superpowers@git+https://github.com/obra/superpowers.git#v7.0.0"]
}
```

Для V2 версии 2.0.4 или новее:

```json
{
  "plugins": ["superpowers@git+https://github.com/obra/superpowers.git#v7.0.0"]
}
```

Добавьте соответствующее поле в существующий `opencode.json`, сохранив остальные настройки. Затем перезапустите OpenCode. Обратите внимание на различие `plugin` и `plugins`.

Тег в примере фиксирует версию плагина. Без него установка следует текущему состоянию репозитория, хотя кеш или lock-файл могут удерживать предыдущую ревизию.

### Другие среды

В репозитории есть инструкции для Codex, Gemini CLI, Pi, Qwen Code и других агентов. Используйте [раздел установки в README](https://github.com/obra/superpowers#installation): переносить команды одного клиента в другой нельзя.

Поддержка skills не обязательно означает наличие субагентов, выбора модели для каждой роли или одинаковой работы hooks.

### Как проверить подключение

Откройте новую сессию и попросите:

```text
Покажи доступные skills Superpowers. Загрузи brainstorming.
Затем помоги спроектировать маленькую CLI-утилиту учёта задач.
До согласования требований код не пиши.
```

Проверяйте три вещи:

1. Среда действительно обнаружила skills, а агент загрузил нужный файл через доступный инструмент.
2. Агент сначала обсуждает недостающие требования, а не сразу создаёт приложение.
3. После согласования он способен перейти к плану, запуску тестов и проверке изменений.

Фраза агента «Superpowers включён» сама по себе ничего не подтверждает. Если skill не найден, проверяйте установку, версию клиента и журнал загрузки. Для диагностики поведения плагина предусмотрен `diagnosing-superpowers`.

## 4. Основные skills

| Skill | Когда нужен | Что должен дать |
|---|---|---|
| `using-superpowers` | Начало работы | Выбор применимых skills |
| `brainstorming` | Новая функциональность, неясная задача | Согласованное описание результата |
| `writing-plans` | Многошаговая реализация | План с файлами, интерфейсами, тестами и проверками |
| `using-git-worktrees` | Нужна изолированная рабочая копия | Подготовленная среда и исходный результат тестов |
| `subagent-driven-development` | Исполнение с отдельными ролями | Исполнитель и ревью каждой задачи, финальное ревью ветки |
| `executing-plans` | Исполнение в одной сессии | Последовательная реализация и финальное ревью |
| `test-driven-development` | Новое поведение или исправление | Цикл RED → GREEN → REFACTOR |
| `systematic-debugging` | Баг, падение теста, неожиданное поведение | Проверенная причина и обоснованное исправление |
| `requesting-code-review` | Нужна проверка изменений | Замечания к конкретному диапазону изменений |
| `receiving-code-review` | Получены замечания | Проверка их обоснованности и исправления |
| `verification-before-completion` | Перед заявлением о готовности | Свежие результаты проверок |
| `finishing-a-development-branch` | Работа закончена | Решение об интеграции или сохранении ветки |
| `dispatching-parallel-agents` | Есть независимые задачи | Разделение независимых исследований или работ |
| `writing-skills` | Нужно создать или улучшить skill | Инструкция, проверенная на сценариях применения |
| `diagnosing-superpowers` | Сам процесс работает неправильно | Разбор сбоя использования Superpowers |

Обычно skills активируются по смыслу запроса. Вручную указывать нужный skill полезно для обучения и при сбоях автоматического выбора:

```text
Используй superpowers:systematic-debugging.
Сначала воспроизведи проблему и установи причину, затем исправляй.
```

Это обычный текст запроса, а не универсальная slash-команда. Способ прямого вызова skills зависит от клиента.

## 5. Полный рабочий цикл

### Шаг 1. Описать задачу и ограничения

Хороший исходный запрос содержит цель, текущий контекст, ограничения и наблюдаемый результат.

```text
В существующем Python CLI нужно добавить экспорт задач в CSV.
Поля: id, title, status. Кодировка UTF-8, первая строка — заголовок.
Существующие команды и формат SQLite не менять.
Сначала уточни неоднозначности и согласуй описание, затем подготовь план.
```

Разработчик проверяет, не придумал ли агент лишние требования: веб-интерфейс, аккаунты, брокер сообщений, отдельный сервис экспорта.

В текущем `brainstorming` масштаб процесса зависит от задачи: ясная мелкая правка может выполняться сразу, небольшое изменение согласуется в чате, проект получает письменное описание. Для исследовательского прототипа предусмотрен облегчённый путь. Поэтому неверно считать, что любая замена строки требует многостраничной спецификации.

### Шаг 2. Согласовать спецификацию

Спецификация отвечает на вопрос «что должно получиться». В ней нужны правила поведения, ограничения и границы задачи.

Путь по умолчанию:

```text
docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
```

Для проекта skill предусматривает проверку документа свежим агентом с позиции будущего исполнителя. Если субагенты недоступны, предусмотрена самостоятельная проверка. Перед реализацией разработчик согласует описание.

Проверяйте прежде всего конкретные условия: что происходит при пустом вводе, повторном запросе, отсутствии записи, ошибке хранилища. Красивое описание архитектуры не компенсирует отсутствие этих правил.

### Шаг 3. Составить план реализации

План отвечает на вопрос «какими изменениями получить результат».

Путь по умолчанию:

```text
docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md
```

Для каждой задачи нужны файлы, точные интерфейсы, проверяемое поведение и команды проверки. Между задачами должны совпадать имена функций, типы и договорённости.

Слабая задача: «Добавить хранение и покрыть тестами».

Рабочая задача: «Реализовать `TaskRepository.add(title: str) -> Task` в `taskbook/repository.py`; проверить создание записи и чтение после повторного открытия БД в `tests/test_repository.py`; использовать временный файл SQLite».

**План не должен превращаться в полный листинг будущей программы.** В актуальном `writing-plans` акцент сделан на точных решениях, интерфейсах и тестах; тела очевидных функций переписывать в документ не требуется. Краткий README может описывать процесс грубее, чем специализированный skill.

### Шаг 4. Подготовить рабочую копию

Git worktree — дополнительный рабочий каталог того же репозитория, обычно с отдельной веткой. Он позволяет не перемешивать новую задачу с текущей работой.

Superpowers сначала проверяет, нет ли уже изоляции, и учитывает инструменты платформы и предпочтения пользователя. В новой рабочей копии нужно подготовить окружение и запустить исходные тесты. Если они уже падают, это фиксируется до изменения кода.

Worktree не является контейнером или sandbox: процессы по-прежнему могут обращаться к общей файловой системе, сети и сервисам. Для тестов нужны отдельные временные данные.

### Шаг 5. Выбрать способ исполнения

| Вопрос | `subagent-driven-development` | `executing-plans` |
|---|---|---|
| Кто реализует | Отдельный исполнитель на задачу | Основной агент в текущей сессии |
| Когда проходит ревью | После задачи и по всей ветке в конце | По всей ветке в конце |
| Контекст | Заново подготовленный для каждой задачи | Накапливается в одной сессии |
| Учёт прогресса | Файловый журнал | Файловый журнал |
| Затраты | Дополнительные вызовы исполнителей и ревьюеров | Меньше отдельных контекстов |
| Когда удобно | Нужны промежуточные проверки, план достаточно большой | Компактный план, ограниченный бюджет, нет инструмента субагентов |

При наличии субагентов финальный обзор inline-исполнения тоже можно поручить свежему ревьюеру. Если их нет, нельзя выдавать самопроверку за независимое ревью; для занятия можно открыть отдельную сессию вручную.

**Subagent-driven не означает параллельную запись кода несколькими агентами.** В рассматриваемой версии основной skill запрещает запускать несколько исполнителей одновременно: они могут конфликтовать при изменении файлов. Параллельная работа выделена в отдельный skill и требует независимости задач.

### Шаг 6. Реализовывать через TDD

Для нового поведения цикл выглядит так:

1. Записать тест ожидаемого поведения.
2. Запустить его и увидеть ожидаемый провал.
3. Написать минимальную реализацию.
4. Убедиться, что тест проходит.
5. Улучшить структуру, сохраняя тесты зелёными.

Падение из-за опечатки или неверно настроенного окружения не доказывает отсутствие нужной функции. Нужно понять причину провала.

Запрос для учебного режима:

```text
Реализуй следующую задачу через test-driven-development.
Для одного нового поведения покажи команду и причину RED,
затем изменение и результат GREEN. Не подменяй это написанием тестов
после готовой реализации.
```

Не следует понимать строгую формулировку skill об удалении кода, написанного до тестов, как разрешение удалять чужой существующий код. Для существующей системы сначала устанавливают поведение и добавляют недостающие проверки.

### Шаг 7. Провести ревью

У исполнителя и ревьюера разные задачи. Исполнитель строит решение; ревьюер ищет расхождения и дефекты.

В рассматриваемой версии ревью задачи объединено в одного ревьюера с двумя отдельными выводами:

- **Соответствие требованиям:** всё ли сделано, нет ли лишнего поведения.
- **Качество реализации:** корректность, понятность, тесты, риски сопровождения.

Это не обязательно два разных агента. Кроме проверки задач, проводится широкое финальное ревью всей ветки.

Ревьюеру передают требования, отчёт исполнителя и diff. Для задачи из нескольких коммитов нужен диапазон от состояния **до начала задачи** до текущего состояния. `HEAD~1..HEAD` покажет только последний коммит и может скрыть основную реализацию.

Ревьюер читает изменения, а не просто соглашается с отчётом «всё готово». Самопроверка исполнителя не заменяет отдельную проверку.

### Шаг 8. Исправить замечания и проверить готовность

Замечание ревьюера — проверяемая гипотеза, а не приказ. Его нужно сопоставить с требованиями и кодом. Ошибочное замечание отклоняют с обоснованием; настоящий дефект исправляют и проверяют тестом.

В версии 7.0.0 циклы исправлений ограничены. Для задачи предусмотрено до пяти раундов, после чего координатор фиксирует решения по оставшимся замечаниям. Финальное ревью также не предполагает бесконечного перезапуска всех проверяющих.

Из этого следует практическое правило: **метка «задача завершена» не всегда означает, что замечаний не осталось**. В итоговом отчёте нужно прочитать отложенные проблемы и решения координатора, особенно раздел `Rulings I made`.

Перед завершением запускают проверки на финальном состоянии кода. Затем выбирают: интегрировать ветку, отправить её на PR или сохранить для дальнейшей работы. Готовая ветка и опубликованное приложение — разные результаты.

## 6. Связь с SDD, TDD, DDD и архитектурой

| Подход | Как связан с Superpowers |
|---|---|
| Spec-driven development | Спецификация задаёт поведение, план связывает его с изменениями, ревью сверяет результат |
| Test-driven development | Отдельный skill задаёт порядок: тест, провал, реализация, успешная проверка |
| Domain-driven design | Можно применять при анализе предметной области; полный DDD-процесс плагином не обеспечивается |
| SOLID и чистая архитектура | Могут быть ограничениями проекта, но автоматически не гарантируются |
| Code review | Встроен в процесс исполнения и завершения |
| CI/CD | Внешний механизм проверки и доставки; его ещё нужно настроить |

Сокращение **SDD неоднозначно**: в материалах по разработке оно может означать spec-driven development, а в названиях рабочих файлов Superpowers — subagent-driven development. В обсуждении лучше называть подход полностью.

Не требуйте от учебной CLI-утилиты десятки интерфейсов и слоёв только ради демонстрации архитектуры. Выделяйте части, у которых действительно различаются обязанности: разбор аргументов, правила поведения, хранение.

## 7. Практикум: CLI-менеджер задач на Python

**Цель:** пройти процесс разработки с агентом и предъявить проверяемые результаты каждого этапа.

**Ориентир по времени:** две пары по 90 минут при заранее подготовленной среде. Это учебная оценка, а не обещание скорости модели. Установку и доступ к агенту лучше проверить до занятия.

**Стек:** Python 3.11+, стандартные `argparse` и `sqlite3`, `pytest` для тестов. Веб-сервер, Docker, ORM и внешние API не нужны.

### 7.1. Задание

Создать CLI `taskbook`:

```bash
python -m taskbook --db tasks.db add "Подготовить доклад"
python -m taskbook --db tasks.db list
python -m taskbook --db tasks.db done 1
python -m taskbook --db tasks.db list --status done
```

Требования:

| ID | Требование |
|---|---|
| R1 | `add` создаёт задачу с целочисленным ID и статусом `todo` |
| R2 | Краевые пробелы заголовка удаляются; пустой результат запрещён |
| R3 | `list` возвращает задачи в порядке возрастания ID |
| R4 | `done` переводит существующую задачу в `done` |
| R5 | Повторное завершение уже выполненной задачи успешно и не создаёт новую запись |
| R6 | Неизвестный ID: понятное сообщение в stderr и ненулевой код выхода |
| R7 | `list --status todo` и `list --status done` фильтруют выдачу |
| R8 | Данные сохраняются между отдельными запусками процесса |
| R9 | `--db` задаёт файл БД; отсутствующий файл в существующем каталоге создаётся автоматически |
| R10 | Ожидаемые ошибки пользователя не выводят traceback; данные при ошибке не теряются |

Для воспроизводимости зафиксируйте формат: `add` печатает ID, `done` печатает `OK`, `list` выводит по строке `id<TAB>status<TAB>title`; пустой список ничего не печатает. Табуляция и переносы строк в заголовке запрещены. При успехе код выхода 0, при ожидаемой ошибке — 2. Точный текст ошибки может отличаться, но должен объяснять причину.

Однопользовательский режим. Одновременные записи несколькими процессами, авторизация, удаление задач и веб-интерфейс не входят в задание.

### 7.4. Получить и проверить план

```text
Спецификация согласована. Используй writing-plans.
Разбей реализацию на небольшое число проверяемых задач.
Укажи файлы, интерфейсы, тесты, команды проверки и зависимости задач.
Свяжи каждое требование R1–R10 с проверкой.
Пока не выполняй план.
```

Возможное разбиение, которое студент должен оценить, а не слепо скопировать:

1. Добавление задач, валидация и сохранение в SQLite.
2. Получение списка и фильтрация.
3. Завершение задачи и обработка неизвестного ID.
4. CLI, коды выхода и проверки между отдельными запусками.

Вспомогательные настройки включаются в задачу, которой они нужны. Создание пустого каталога не заслуживает отдельного исполнителя и ревьюера.

**Результат:** план, где каждую задачу можно отдельно проверить.

### 7.5. Выполнить план

Основной вариант занятия:

```text
План согласован. Выполни его через subagent-driven-development.
Разрешаю создать отдельный worktree и ветку для этой задачи,
делать локальные коммиты и запускать тесты.
Используй TDD, ревью каждой задачи и финальное ревью ветки.
После реализации сохрани ветку; push и merge пока не выполняй.
В конце покажи diff-статистику, результаты проверок,
отложенные замечания и принятые без меня решения.
```

Экономный вариант:

```text
План согласован. Выполни его через executing-plans в текущей сессии.
Используй TDD и журнал прогресса, затем проведи финальное ревью.
Если отдельный ревьюер недоступен, сообщи об этом: ревью выполним
в новой сессии. Сохрани результат в отдельной ветке без push и merge.
```

Во время выполнения студент следит за одним полным циклом RED → GREEN и одним ревью. Не нужно читать каждый промежуточный токен агента.

### 7.6. Пример одного TDD-шага

Предположим, в плане согласован интерфейс:

```python
def normalize_title(title: str) -> str:
    ...
```

Создайте функцию-заглушку, чтобы тест проверял поведение, а не падал на импорте:

```python
# taskbook/domain.py

def normalize_title(title: str) -> str:
    return title
```

Сначала тест:

```python
# tests/test_domain.py
import pytest
from taskbook.domain import normalize_title


def test_rejects_blank_title():
    with pytest.raises(ValueError):
        normalize_title("   ")
```

Запуск:

```bash
python -m pytest tests/test_domain.py::test_rejects_blank_title -q
```

Ожидаемый RED: исключение не возникло. Это описание ожидаемого результата, а не журнал фактического запуска учебного проекта.

Минимальное изменение:

```python
def normalize_title(title: str) -> str:
    title = title.strip()
    if not title:
        raise ValueError("Заголовок не должен быть пустым")
    return title
```

Повторите запуск и получите GREEN. Затем отдельными циклами проверьте удаление краевых пробелов и запрет табуляции и переводов строк. Показанная функция — промежуточная реализация, а не полное решение задания.

**Вопрос студенту:** почему один успешный тест на пустую строку не доказывает выполнение всего требования к заголовку?

### 7.7. Проверить результат независимо от отчёта агента

Запустите:

```bash
python -m pytest -q
python -m taskbook --db demo.db add "  Проверить сохранение  "
python -m taskbook --db demo.db list
```

Используйте новый файл `demo.db` в текущем учебном каталоге. Возьмите ID из вывода `add`, а не предполагайте, что он всегда равен 1.

Далее проверьте вручную:

- завершение задачи и повторное завершение;
- фильтры `todo` и `done`;
- неизвестный ID;
- пустой заголовок;
- сохранение данных после закрытия процесса и нового запуска.

Автоматические CLI-тесты должны использовать временный файл БД и отдельные процессы, например через `subprocess.run`. Проверка в одном объекте репозитория не доказывает сохранение данных между запусками.

### 7.8. Добавить вторую итерацию: CSV

После завершения первой версии дайте новое требование:

```text
Добавь команду export --output tasks.csv.
Экспортируются все задачи по возрастанию ID.
UTF-8, заголовок id,title,status.
Используй стандартный модуль csv; запятые и кавычки в title
должны корректно сохраняться. Существующий файл не перезаписывать:
вернуть понятную ошибку и код 2.
Проведи изменение через описание, план, TDD и ревью.
```

Проверки: пустая БД, кириллица, запятая в заголовке, кавычки, существующий файл назначения. Содержимое проверяйте через `csv.reader`, а не самодельное разбиение по запятым.

**Результат:** новая функция, проверенная вместе с прежними тестами. Это демонстрация итеративной разработки, а не генерация всего приложения одним запросом.

### 7.9. Отработать исправление бага

В отдельной учебной ветке преподаватель меняет сортировку выдачи на убывающую. Если имеющийся тест сразу падает, это ожидаемая работа защиты от регрессии.

Запрос агенту:

```text
Список задач нарушает порядок, заданный спецификацией.
Используй systematic-debugging. Воспроизведи проблему,
покажи причину, добавь недостающий регрессионный тест при необходимости,
выполни минимальное исправление и проверь весь набор тестов.
```

Не сообщайте агенту заранее конкретную строку ошибки: цель — увидеть исследование причины. Если тест уже существует, не требуйте дублирующий тест ради отчёта.

1. Репозиторий с историей коммитов.
2. Спецификацию и план.

Не полагайтесь на сохранность временного журнала `.superpowers/`: он может очищаться при завершении. Учебные свидетельства сохраните отдельно в `docs/lab-report.md` до очистки.

Оценка из 10 баллов: требования и план — 2; корректное поведение — 3; тесты и настоящий TDD-цикл — 2; ревью и работа с замечаниями — 2; воспроизводимый запуск и объяснение решения — 1.

## 8. Как вести существующий проект

Начинайте с небольшого изменения, чтобы проверить совместимость процесса с репозиторием.

```text
Изучи правила репозитория, структуру и существующие тесты.
Нужно изменить только [конкретное поведение].
Сохрани публичные интерфейсы и стиль проекта.
Не обновляй зависимости и не перестраивай архитектуру без необходимости.
Зафиксируй исходный результат тестов, предложи небольшой план,
после согласования реализуй его и организуй ревью diff.
```

Если тестов нет, сначала добавьте проверки поведения изменяемого участка. Если они падают до правки, отделите исходную проблему от новой. Не превращайте маленькую задачу в переписывание всего проекта.

Долгоживущие правила держите в проектных инструкциях, которые читает конкретная среда: например, `AGENTS.md` или `CLAUDE.md`. Там полезны реальные команды тестирования, ограничения зависимостей, договорённости о совместимости и запрещённые области изменений. Правила одной функции принадлежат её спецификации, а не глобальным инструкциям.

После перерыва дайте агенту пути к спецификации и плану, попросите проверить Git и журнал прогресса. Реплика «продолжай» без восстановления состояния может привести к повторной реализации уже сделанной задачи.

## 9. Типичные ошибки и пределы подхода

| Ошибка | Что делать |
|---|---|
| Сразу просить большое приложение целиком | Согласовать ограниченный первый результат |
| Утверждать план, не читая | Проверить границы, интерфейсы и критерии готовности |
| Считать текст «тесты прошли» доказательством | Проверить команду, результат и состояние кода |
| Просить ревью только последнего коммита | Передать весь диапазон задачи или ветки |
| Принимать все замечания ревьюера | Проверять их по требованиям и коду |
| Запускать исполнителей параллельно в общих файлах | Разделить работу или выполнять последовательно |
| Считать worktree изоляцией от системы | Отдельно ограничить разрешения и тестовые ресурсы |
| Игнорировать отложенные дефекты | Прочитать итоговые решения и оценить последствия |
| Считать зелёные тесты полной приёмкой | Проверить покрытие требований и реальные сценарии |

Польза Superpowers — в повторяемом процессе и проверяемых промежуточных результатах. Это разумный инженерный механизм, но из документации не следует количественная гарантия повышения качества для вашей модели и репозитория.

Новый контекст ревьюера помогает избежать части предубеждений исполнителя, но ошибки агентов могут быть коррелированными: одинаковая модель и одинаково неверная спецификация способны породить одинаковое заблуждение. Человеческое ревью, интеграционные тесты и CI сохраняют самостоятельную ценность.

Субагенты также стоят времени и токенов. Для небольшой задачи процесс может оказаться дороже самой правки. Сравнивайте варианты на одинаковых задачах по времени до принятого результата, затратам и числу пропущенных дефектов — количество запущенных агентов само по себе ничего не измеряет.

## 10. Краткая памятка

1. Опишите нужное поведение и границы.
2. Проверьте спецификацию и план.
3. Выберите исполнение: с ревью каждой задачи или inline.
4. Убедитесь, что агент действительно запускает тесты.
5. Проверьте весь diff, замечания и отложенные решения.
6. Принимайте результат по выполнению требований, а не по уверенности отчёта.
