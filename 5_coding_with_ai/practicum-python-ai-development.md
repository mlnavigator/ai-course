# Практикум: разработка Python-приложения с ИИ по DDD, SDD и TDD

## 1. Что предстоит сделать

Разработайте **LabLend — приложение для выдачи оборудования учебной лаборатории**. Студенты берут камеры, ноутбуки и измерительные приборы, возвращают их, иногда задерживают возврат. Сотрудник лаборатории должен видеть, кто и чем пользуется, и не выдавать недоступное оборудование.

Вы будете постепенно добавлять возможности к одному проекту. На каждом этапе нужно уточнить требования, обновить модель, написать спецификацию, реализовать поведение через тесты и передать ветку отдельному агенту-ревьюеру.

**Итог:** запускаемое Python-приложение с CLI, SQLite, тестами, спецификациями и историей развития. Веб-интерфейс не нужен. FastAPI — дополнительное задание после основной части.

**Формат:** индивидуально или в паре. Ориентир — четыре занятия по 90 минут и самостоятельная работа; время зависит от опыта программирования и владения агентом. Сокращённый вариант — этапы 0–3 без SQLite, полный — этапы 0–5.

**Необходимые знания:** функции и классы Python, исключения, модули, основы Git. SQL потребуется на последнем этапе.

### Какие подходы применяются

| Подход | Что вы делаете своими руками |
| --- | --- |
| DDD | Выделяете понятия, правила, состояния, границы ответственности и согласованности |
| SDD | До изменения кода пишете спецификацию конкретной возможности и сверяете с ней результат |
| TDD | Получаете падающий тест нового поведения, реализуете его, затем рефакторите |
| BDD | Уточняете поведение сценариями «дано — когда — тогда» |
| SOLID, Clean Architecture | Разделяете правила, сценарии и технические адаптеры там, где это полезно |
| KISS, YAGNI | Не создаёте ненужные слои и будущие возможности |
| Агентное ревью | Поручаете отдельному агенту проверку всей ветки, разбираете замечания |
| Человеческая приёмка | Проверяете смысл, модель, структуру, простоту и существенные риски |

**Важно:** TDD — не «сначала агент написал весь код, потом добавил тесты». В этом практикуме тест нового поведения появляется раньше его рабочей реализации.

## 2. Исходная постановка заказчика

> В лаборатории есть конкретные экземпляры оборудования. Два одинаковых ноутбука — два разных экземпляра. У каждого свой инвентарный номер. Студент может взять оборудование на определённый срок. Нужно хранить историю выдач, принимать возвраты и понимать, доступен ли экземпляр. Позже понадобятся ограничения для должников и учёт обслуживания.

Не переводите этот абзац сразу в таблицы БД и классы. Сначала выясните, какие события и правила он описывает.

### Общие условия учебного проекта

- Приложением пользуется доверенный сотрудник лаборатории; аутентификация и роли не реализуются.
- ID студента — идентификатор получателя оборудования, а не доказательство его личности.
- Используются календарные даты `YYYY-MM-DD`, без времени суток. Текущую дату сценарии получают явно; CLI может подставлять её по умолчанию.
- Данные для демонстрации вымышленные.
- В основной части команды исполняются последовательно одним процессом. Конкурентная выдача — отдельное усложнение, а не обещанная гарантия базовой версии.
- Оплата, штрафы, уведомления, бронирование на будущее, очереди ожидания и микросервисы не входят в основную работу.

Это задание про **фактическую выдачу**, а не бронирование интервалов из теоретического материала. Не переносите туда все правила прежнего примера автоматически.

## 3. Как организовать работу

### Инструменты

Python 3.11 или новее, Git, pytest. Для CLI достаточно `argparse`, для хранения — стандартного модуля `sqlite3`. Дополнительные зависимости допустимы, если вы объясняете необходимость.

Пример подготовки на Linux/macOS:

```bash
mkdir lablend
cd lablend
git init
python3 -m venv .venv
source .venv/bin/activate
python -m pip install pytest
python -m pip freeze > requirements-dev.txt
```

На Windows окружение активируется соответствующей командой вашей оболочки. Не добавляйте `.venv`, кэши, локальные БД и секреты в Git. Зафиксируйте используемую версию Python в README. После создания тестов запускайте их из корня проекта командой `python -m pytest`.

Не устанавливайте весь возможный стек заранее. ORM, Docker, веб-сервер и DI-контейнер для основной задачи не требуются.

### Документы проекта

| Файл или каталог | Содержимое |
| --- | --- |
| `README.md` | Установка, запуск, проверки, демонстрационные команды |
| `docs/domain.md` | Словарь, правила, состояния и принятая декомпозиция |
| `docs/decisions.md` | Короткие записи значимых решений и их причин |
| `specs/01-issue.md` и последующие | Спецификации итераций |
| `reviews/` | Отчёты ревьюера и решения по замечаниям |
| `progress.md` | Краткая история этапов и доказательства TDD |
| `AGENTS.md` или аналог вашего агента | Рабочие команды и ограничения |
| Python-пакет и `tests/` | Реализация и проверки |

Названия Python-модулей, классов и интерфейсов выберите самостоятельно. Папки `domain`, `application`, `adapters` допустимы, но не обязательны: оценивается разделение ответственности, а не совпадение структуры с шаблоном.

### Что студент должен сделать сам

До обращения к агенту составьте черновик модели и минимум три примера поведения. Затем используйте ИИ для критики и доработки. Для каждой итерации самостоятельно добавьте хотя бы один тест или существенное утверждение, которого не предложил исполнитель.

Агенту разрешено писать код, тесты и документацию. Вы отвечаете за согласованные требования и должны уметь объяснить реализацию. Полная генерация проекта одним запросом не выполняет цель практикума.

## 4. Этап 0. DDD: разобрать предметную область

На этом этапе рабочий код не нужен.

### Задание 0.1. Словарь

Выделите 6–10 терминов. Для каждого запишите значение, пример и то, с чем его нельзя путать. Обязательно разберите:

- тип оборудования и конкретный экземпляр;
- студента и запись о выдаче;
- факт возврата и доступность экземпляра;
- срок возврата и просрочку;
- обслуживание и занятость.

### Задание 0.2. Сценарии и события

Перечислите действия сотрудника и результаты, важные для предметной области. Например, команда «выдать экземпляр» приводит к факту «экземпляр выдан».

События здесь нужны для анализа. Создавать event bus, брокер сообщений или event sourcing не требуется.

### Задание 0.3. Модель и границы

Ответьте письменно:

1. Какие объекты имеют самостоятельную идентичность?
2. Какие значения достаточно сравнивать по содержимому?
3. Какие правила должны оставаться истинными после любой успешной операции?
4. Какие данные нужно менять согласованно?
5. Как предотвратить две активные выдачи одного экземпляра в последовательном сценарии?
6. Какие области ответственности видны: каталог, выдачи, обслуживание? Нужны ли им отдельные bounded contexts уже сейчас?

Предложите границу агрегата или объясните более простую модель. Не считайте, что каждая сущность должна стать отдельным сервисом. Если инвариант охватывает несколько объектов, укажите, кто и как его обеспечивает. Само слово «агрегат» не создаёт атомарность.

### Задание агенту

> Проверь мой словарь и модель LabLend. Найди неоднозначные понятия, пропущенные инварианты и смешение предметных и технических сущностей. Предложи не более двух вариантов декомпозиции и объясни их цену. Не пиши код и не объявляй новые требования согласованными.

**Результат этапа:** `docs/domain.md`, перечень сценариев, одна короткая запись о выбранной структуре и причинах отказа от более сложной альтернативы. Человек принимает модель до начала реализации.

## 5. Цикл каждой итерации

Повторяйте этот порядок на этапах 1–5.

1. **Спецификация:** цель, правила, ошибки, примеры, границы задачи.
2. **План:** минимальное изменение модели и кода, затрагиваемые файлы, проверки.
3. **TDD:** один следующий сценарий, падающий тест, реализация, зелёные тесты, рефакторинг.
4. **Регрессия:** предыдущие согласованные сценарии продолжают работать.
5. **Агентное ревью:** отдельная сессия проверяет ветку относительно базы.
6. **Разбор:** подтверждённые ошибки исправляются, отклонения объясняются, исправления перепроверяются.
7. **Приёмка:** студент проверяет смысл, DDD, структуру, KISS/YAGNI и критичные детали; сохраняет рабочую версию.

Для каждой итерации создайте ветку, например `feature/01-issue`, от принятой версии. Отметьте базовый коммит. Итог ревью должен относиться к конкретному коммиту; изменения после ревью требуют проверки.

### Шаблон спецификации

```markdown
# Итерация N: название
## Цель пользователя
## Входит в изменение
## Не входит
## Термины и правила
R1. ...
## Контракт операции
Вход, результат, ошибки, изменение состояния при успехе и отказе.
## Примеры приёмки
AC1. Дано ... Когда ... Тогда ...
## Изменения предыдущих правил
Что заменяется, что сохраняется и почему.
## Проверка
Какие тесты и демонстрационные сценарии подтверждают результат.
```

### Как показать настоящий TDD

В каждой итерации сохраните один короткий пример в `progress.md`:

```text
Требование: нельзя повторно выдать занятый экземпляр.
RED: команда проверки и фактическое падение на ожидаемом утверждении.
GREEN: что добавлено в реализацию; фактический результат запуска.
REFACTOR: что упрощено и как проверено сохранение поведения.
Коммиты или иной проверяемый след изменения: ...
```

Ошибка установки pytest не является RED нужного поведения. Отсутствующая функция может быть первым техническим препятствием, но для демонстрации создайте заглушку и получите падение, связанное именно с новым правилом.

Не нужно коммитить каждый красный тест в общую ветку. Достаточно проверяемой истории в рабочей ветке или сохранённых результатов этапов. Не придумывайте логи задним числом.

## 6. Итерация 1. Каталог и первая выдача

### Заказчик просит

> Хочу добавить экземпляры оборудования, выдать конкретный экземпляр студенту и посмотреть текущие выдачи. Занятый экземпляр нельзя выдать ещё раз.

### Правила

- У экземпляра уникальный непустой инвентарный номер и непустое название. Для строк сначала удаляются пробелы по краям; регистр ID значим.
- Повторное добавление того же номера отклоняется, существующая запись не изменяется.
- Выдача содержит собственный уникальный ID, номер экземпляра, непустой ID студента, дату выдачи и срок возврата.
- Срок возврата не раньше даты выдачи. Выдача и возврат в один день допустимы.
- У экземпляра не более одной активной выдачи.
- Неизвестный экземпляр и некорректные входные данные вызывают явную ошибку; состояние не меняется.
- Отдельный реестр студентов пока не нужен: достаточно непустого ID получателя.

Хранение на этом этапе — в памяти. Клиентский интерфейс пока может быть обычным Python-вызовом; CLI появится на этапе 5.

### Что сделать

1. Подготовьте `specs/01-issue.md`.
2. Выберите минимальную модель и контракт сценария выдачи.
3. Реализуйте добавление, выдачу, получение экземпляра и список активных выдач.
4. Добавьте понятные ошибки: исключения или явные результаты. Выбранный способ должен быть единообразным.

### Обязательные проверки

| Ситуация | Ожидается |
| --- | --- |
| Добавлен `CAM-01`, выдан `S-01` на допустимые даты | Одна активная выдача с ID |
| `CAM-01` пытаются выдать `S-02` | Отказ, первая выдача сохранена |
| Выдают другой свободный `CAM-02` | Успех |
| Добавляют `CAM-01` повторно | Отказ, прежнее название сохранено |
| Срок раньше даты выдачи | Отказ, новой выдачи нет |
| ID студента состоит из пробелов | Отказ |
| Выдают неизвестный экземпляр | Отказ без изменения состояния |

Для первого TDD-цикла возьмите успешную выдачу, затем добавьте запрет повторной. Не реализуйте пока возврат и лимит студента.

**Приёмка:** агент-ревьюер проверил ветку, студент может показать, где обеспечивается единственность активной выдачи.

## 7. Итерация 2. Возврат и история

### Заказчик просит

> Хочу принимать возврат и выдавать вернувшийся экземпляр снова. История прежних выдач должна сохраняться.

### Новые правила

- Возврат выполняется по ID выдачи и содержит дату возврата.
- Дата возврата не раньше даты выдачи; поздний возврат допустим.
- Возврат закрывает выдачу и освобождает экземпляр.
- Повторный возврат уже закрытой выдачи отклоняется; первая дата возврата сохраняется.
- Неизвестный ID выдачи вызывает явную ошибку.
- После возврата новая выдача получает новый ID; старая остаётся в истории.

### Задание по DDD

Обновите описание состояний. Ответьте: «экземпляр занят» — самостоятельный источник данных или вывод из активной выдачи? Если храните оба представления, как исключаете рассогласование?

### Обязательные проверки

1. Выдать → вернуть → выдать другому студенту: две записи истории, одна активная.
2. Дважды вернуть первую выдачу: второй вызов отклонён, история не повреждена.
3. Вернуть до даты выдачи: отказ, экземпляр всё ещё занят.
4. Вернуть в день выдачи: успех.
5. Вернуть неизвестную выдачу: отказ без изменений.

**Важно:** нельзя просто удалить запись выдачи при возврате. Это нарушает требование истории.

**Приёмка:** работающие старые тесты, новая спецификация, хотя бы один TDD-цикл, агентное ревью и разбор замечаний.

## 8. Итерация 3. Лимит и просрочка

### Заказчик просит

> Студент может держать одновременно не более двух экземпляров. Если хотя бы один просрочен, ничего нового ему выдавать нельзя. Вернуть оборудование он может всегда, если сам возврат корректен.

### Новые правила

- Лимит — две активные выдачи на студента.
- Активная выдача просрочена, если дата проверки **строго позже** срока возврата.
- В последний день срока просрочки ещё нет.
- Возвращённая выдача не считается просроченной для запрета новых выдач, даже если её вернули поздно.
- Ограничения проверяются на дату новой выдачи, переданную в сценарий.
- Новое правило не отменяет прежние выдачи и не запрещает возвраты.
- В этой итерации вводятся отчёт о текущих просрочках на заданную дату и фильтр активных выдач по студенту. Исторический отчёт «как было на прошлую дату» не требуется.

### Задание по DDD

Кто проверяет лимит — экземпляр, выдача, студент или прикладной сценарий? Как получить необходимые данные? Обоснуйте выбор; не создавайте сущность студента только ради появления ещё одного класса.

### Таблица приёмки

| Текущее состояние студента | Действие | Результат |
| --- | --- | --- |
| Одна непросроченная выдача | Взять второй экземпляр | Успех |
| Две непросроченные выдачи | Взять третий | Отказ |
| Срок первой выдачи 2030-04-12 | Взять второй 2030-04-12 | Успех |
| Та же активная выдача | Взять второй 2030-04-13 | Отказ |
| Просроченный экземпляр возвращён | Взять свободный, лимит позволяет | Успех |
| Две активные выдачи, одна просрочена | Вернуть её корректной датой | Успех |

Каждая строка — независимая фикстура, если явно не указано другое. Не стройте весь набор тестов как один зависимый сценарий.

### Изменение прежних требований

Раньше число выдач не ограничивалось, теперь ограничено. Если старый тест намеренно проверял три активные выдачи, его нужно пересмотреть со ссылкой на новое требование. Это отличается от ослабления теста ради ошибочной реализации.

**Упражнение:** временно замените проверку `date > due_date` на `date >= due_date`. Покажите тест, обнаруживший ошибку, затем восстановите код. Саму формулу в проекте найдите самостоятельно.

## 9. Итерация 4. Обслуживание оборудования

### Заказчик просит

> Оборудование можно отправить на обслуживание. Если его держит студент, сначала надо принять возврат. После обслуживания экземпляр снова можно выдавать.

### Новые правила

- Свободный экземпляр можно отправить на обслуживание с непустой причиной.
- Занятый экземпляр отправить на обслуживание нельзя; операция отклоняется без изменений.
- На обслуживании экземпляр выдавать нельзя.
- Повторное начало обслуживания отклоняется.
- Завершить можно только начатое обслуживание; после завершения экземпляр доступен при отсутствии других препятствий.
- Причина сохраняется для текущего обслуживания. Полная история ремонтов в базовое задание не входит.

### Задание по DDD

Обновите модель и таблицу допустимых переходов. Ответьте: «занят» и «на обслуживании» — значения одного перечисления или разные аспекты состояния? Какие противоречивые комбинации ваша модель допускает и как предотвращает?

Не требуется единственный «правильный» вариант классов. Требуется понятная модель, обеспечивающая заданные правила.

### Обязательные проверки

- Свободен → обслуживание → попытка выдачи: отказ.
- Обслуживание → завершение → выдача: успех.
- Выдан → попытка обслуживания: отказ, выдача остаётся активной.
- Выдан → возврат → обслуживание: успех.
- Повторное начало и завершение без начала: отказ.
- Пустая причина: отказ без изменения состояния.

### Ревью структуры

Попросите агента указать, где новое поведение потребовало изменения старого кода. Человек отвечает: изменения локальны по смыслу или правило размазано по CLI, хранению и модели? Нужен ли небольшой рефакторинг? Достаточно ли простой функции вместо нового набора стратегий?

## 10. Итерация 5. SQLite и работающий CLI

### Заказчик просит

> Программа должна сохранять данные между запусками. Сотрудник должен выполнять операции из терминала.

### Что сделать

1. Реализуйте постоянное хранение в SQLite.
2. Сделайте CLI для добавления экземпляра, выдачи, возврата, просмотра активных выдач и истории, обслуживания и просмотра просрочек.
3. Сохраните прежние бизнес-правила. Они не должны заново реализовываться внутри CLI.
4. Покройте хранение интеграционными тестами на временной файловой БД.
5. Сделайте создание новой БД воспроизводимым и недеструктивным при повторном запуске.

### Предлагаемый интерфейс команд

Имена команд можно изменить, но тогда отразите свой интерфейс в README. Ниже целевой контракт, который вам предстоит реализовать, а не уже работающая программа:

```bash
python -m lablend --db demo.sqlite init
python -m lablend --db demo.sqlite add-item CAM-01 "Камера"
python -m lablend --db demo.sqlite issue CAM-01 S-01 --on 2030-04-10 --due 2030-04-12
python -m lablend --db demo.sqlite active --student S-01
python -m lablend --db demo.sqlite overdue --on 2030-04-13
```

Команда выдачи выводит ID новой выдачи. Его используют для возврата. Для ожидаемой ошибки нужна понятная диагностика и ненулевой код завершения; traceback не должен быть обычным способом сообщить «экземпляр занят».

### Контракт хранения

Если вы выделили абстракцию хранения, повторите общий набор сценариев для реализации в памяти и SQLite. Одинаковые имена методов не гарантируют одинаковую семантику.

Укажите границы транзакций: какие записи должны измениться вместе? При ошибке сохранения нельзя оставлять половину результата. В основной версии не требуется многопроцессная конкурентная работа, но атомарность одной команды требуется.

### Обязательные проверки

- Создать данные, закрыть соединение, открыть БД снова: данные и состояния сохранились.
- Повторная инициализация не удаляет существующие записи.
- ID экземпляра остаётся уникальным.
- Возврат сохраняет историю и освобождает экземпляр после перезапуска.
- Обслуживание продолжает запрещать выдачу после перезапуска.
- Ошибка в операции не оставляет частично сохранённого состояния.
- CLI принимает корректные команды и возвращает ошибку для некорректных данных.
- Хотя бы один CLI-тест запускает команду отдельным процессом, а не только вызывает Python-функцию обработчика.

**Архитектурная проверка:** покажите, что тесты чистых правил запускаются без SQLite и CLI. Добавьте автоматическую проверку запрета зависимостей ядра от адаптеров — выбранным инструментом или небольшой проверкой импортов.

## 11. Агентное ревью на каждой итерации

Исполнитель и ревьюер работают в разных сессиях. Ревьюеру передаются спецификация, модель, исходный базовый коммит и проверяемый коммит ветки, доступ к полному проекту и команды проверки.

### Задание исполнителю

> Реализуй только текущую итерацию по согласованной спецификации. Сначала прочитай модель и существующие тесты. Предложи небольшой план. Реализуй поведение короткими TDD-циклами, запускай тесты фактически. Не добавляй будущую функциональность. В конце укажи изменения, результаты команд и непроверенные ограничения.

### Задание ревьюеру

> Проверь всю ветку текущей итерации относительно базового коммита. Самостоятельно прочитай спецификацию, diff и связанный код. Ищи нарушенные правила, граничные случаи, регрессии, слабые тесты и изменения вне задачи. При необходимости воспроизведи проблему. Продуктовую ветку не исправляй. Для замечания укажи место, условия, последствия и доказательство. Отделяй подтверждённые дефекты от предположений и вопросов к требованиям. Если замечаний нет, укажи границы выполненной проверки.

### Таблица разбора

| ID | Замечание | Доказательство | Решение студента | Исправление и повторная проверка |
| --- | --- | --- | --- | --- |
| R-01 | … | … | Исправить / отклонить / уточнить | Коммит, тест, результат |

Нет требования обязательно найти дефект. Не исправляйте ложное замечание ради согласия с агентом. Отклонение тоже должно быть обосновано.

Человек отдельно принимает DDD, структуру, KISS/YAGNI и смысл изменения. Он также проверяет критичные детали: ограничения выдачи, сохранение истории и атомарность. Зелёные тесты и отсутствие замечаний не заменяют эту работу.

## 12. Финальная демонстрация

Сначала запустите весь набор проверок. Затем на новой БД выполните сценарий. После каждой строки покажите результат и состояние; ожидаемые отказы тоже являются частью успешной демонстрации.

| Шаг | Действие | Ожидается |
| --- | --- | --- |
| 1 | Добавить CAM-01, CAM-02, LAP-01 | Три разных экземпляра |

| 3 | Повторно выдать CAM-01 студенту S-02 | Отказ: занят |

| 6 | Вернуть выдачу B датой 11 апреля | У S-01 одна активная выдача |

Во всех командах выдачи явно задавайте допустимый срок. После шага 2 не используйте дату ранее 10 апреля. Для шагов 10–11 используйте 13 апреля и срок 15 апреля. Конкретные ID A, B, C берутся из результатов команд.

## 13. Дополнительные задания

Выберите одно после работающей основной версии.

### A. Свойства и мутации

Добавьте property-based проверки: число активных выдач экземпляра не больше одного, отказ не меняет состояние, корректный возврат уменьшает число активных выдач студента на один. Определите допустимые входы и последовательности операций. Можно использовать Hypothesis или сначала написать параметризованные проверки вручную.

Запустите мутационную проверку небольшого участка или внесите контролируемую ошибку вручную. Покажите, какой тест её обнаруживает. Не считайте любое число тестов доказательством полноты.

### B. Конкурентная выдача

Два независимых соединения пытаются выдать один экземпляр. Определите контракт: не более одной успешной выдачи, согласованная ошибка проигравшему, отсутствие частичных записей. Выберите транзакционный механизм SQLite по документации и проверьте настоящий конкурентный сценарий. Два последовательных вызова не считаются.

### C. HTTP-адаптер

Добавьте FastAPI поверх прикладных сценариев. Сначала согласуйте контракт запросов, ответов и ошибок. Не переносите правила в HTTP-обработчики. Реализуйте и проверьте две операции — выдачу и возврат. Учебный запуск остаётся локальным, без публичного размещения и без выдачи ID студента за аутентификацию.

### D. Изменение политики

Теперь преподаватели могут держать четыре экземпляра, студенты — два; запрет при просрочке одинаков. Сначала решите, откуда берётся категория получателя. Обновите модель и спецификацию, затем тесты и реализацию. Объясните, потребовалась ли новая абстракция или достаточно простой таблицы правил.

## 15. Рекомендации преподавателю

Выдавайте задания итераций последовательно. Студентам полезно знать общее направление, но не нужно заранее проектировать все будущие расширения. На этапе 0 оценивайте качество обсуждения модели, а не наличие готовых классов.

Один возможный план: первое занятие — модель и выдача; второе — возврат и ограничения; третье — обслуживание и ревью структуры; четвёртое — хранение, CLI и защита. Часть реализации и ревью выполняется самостоятельно.

Чтобы отличить осмысленную работу от генерации целиком, попросите на защите небольшое изменение правила и новый тест к нему. Например, изменить лимит или поведение повторного возврата. Студент должен сначала назвать изменяемое требование и ожидаемый результат, затем показать изменение.

Дефекты для учебной проверки ревью можно вносить только в отдельную копию: включённая граница просрочки, потеря истории, проверка лимита при возврате, пропуск запрета обслуживания. Не выдавайте заранее внесённый дефект за реальную находку в работе студента.

Основной результат практикума — способность управляемо развивать программу: понимать предметную область, задавать поведение, получать проверяемые изменения и принимать результат агента осознанно.
