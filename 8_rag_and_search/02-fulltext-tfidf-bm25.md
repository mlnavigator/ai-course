# 2. Полнотекстовый поиск: обратный индекс, TF-IDF и BM25

Материал для курса по ИИ. Примеры — Python. Проверка документации: 30 октября 2026 года.

**Цель:** понять, как из текста строится индекс, почему совпадения слов имеют разный вес и как ранжировать документы без нейросетей. Код находится в `lexical.py` и `sqlite_search.py` общего проекта.

## 1. Что такое полнотекстовый поиск

Полнотекстовый поиск работает с содержимым документов. Обычно текст разбивается на термы, индексируется, а запрос сопоставляется с индексом. Возможны условия AND/OR, фразы, префиксы, поля и ранжирование.

Это не то же самое, что `if query in text`: подстрока не учитывает структуру слов и не задаёт порядок релевантности. При этом отдельные поисковые системы поддерживают и подстроки, и символьные n-граммы.

Лексический поиск особенно полезен для артикулов, фамилий, кодов ошибок и терминов. Для запроса `E17` совпадение символов может быть существеннее общей смысловой близости текста.

**Обратный индекс — структура данных. TF-IDF и BM25 — способы вычисления веса и релевантности.** Это не три взаимозаменяемых поисковых продукта.

## 2. Подготовка текста

Простейший анализатор:

```python
import re


def tokenize(text):
    return re.findall(r'[\w]+', text.lower().replace('ё', 'е'), flags=re.UNICODE)
```

Пример: «Платёж E17 отклонён» превращается в `['платеж', 'e17', 'отклонен']`.

Одинаковую обработку нужно применять к запросам и документам. Но простота имеет ограничения:

- `карта`, `карты`, `карту` останутся разными термами.
- `C++` станет `c`, то есть значимая часть обозначения потеряется.
- Дефисы и пунктуация могут быть частью артикула.
- Слияние `ё` и `е` допустимо не для каждого вида данных.

**Лемматизация** приводит словоформы к словарной форме; **стемминг** отрезает или преобразует окончания по правилам. Для русского языка можно экспериментировать с `pymorphy3` или Snowball stemmer, но это отдельные анализаторы: их качество и применимость нужно проверять. Смешанному корпусу могут потребоваться разные анализаторы по языкам.

Стоп-слова удаляют часто встречающиеся служебные слова. Не удаляйте механически отрицания: «принимаем наличные» и «не принимаем наличные» описывают разные правила.

## 3. Обратный индекс

Пусть документы после анализа выглядят так:

| ID | Термы |
|---|---|
| A | `возврат деньги карта` |
| B | `оплата карта карта` |
| C | `возврат товар` |

Прямое представление: документ → слова. **Обратное представление: слово → документы, в которых оно встречается.** Список записей для слова называют posting list.

| Терм | Postings с частотами |
|---|---|
| `возврат` | A: 1, C: 1 |
| `деньги` | A: 1 |
| `карта` | A: 1, B: 2 |
| `оплата` | B: 1 |
| `товар` | C: 1 |

Для `возврат AND карта` пересекаются множества `{A, C}` и `{A, B}`: остаётся A. Для OR берётся объединение. Не нужно перечитывать каждый исходный документ для каждого запроса.

В реальном индексе могут храниться позиции слов, поля, частоты и другие сведения. Для точной фразы «возврат товара» одной информации «оба слова есть» недостаточно: нужно проверить порядок и соседство позиций. [1]

Простой индекс на Python:

```python
from collections import Counter, defaultdict

texts = {'A': 'возврат деньги карта', 'B': 'оплата карта карта', 'C': 'возврат товар'}
postings = defaultdict(dict)
for doc_id, text in texts.items():
    for term, count in Counter(text.split()).items():
        postings[term][doc_id] = count

matches = set(postings['возврат']) & set(postings['карта'])
print(matches)  # {'A'}
```

Ускорение зависит от частотности термов и реализации. Очень частое слово имеет длинный posting list. Промышленные системы используют сжатие, пропуски и оптимизации top-k; этот пример их не реализует.

## 4. TF, DF и IDF

**TF — term frequency:** сколько раз терм встречается в конкретном документе.

**DF — document frequency:** в скольких документах корпуса терм встретился хотя бы раз.

**IDF — inverse document frequency:** вес, повышающий значимость термов, редких в корпусе.

Для таблицы выше `TF(карта, B)=2`, а `DF(карта)=2`. Это разные величины.

Один распространённый вариант сглаженного IDF:

\[
\operatorname{idf}(t)=\ln\frac{N+1}{df(t)+1}+1.
\]

При `N=3` слово в одном документе получает `ln(4/2)+1 ≈ 1.693`; слово во всех трёх — 1. Таким образом, редкое слово сильнее различает документы.

IDF не измеряет истинность, важность для бизнеса или качество документа. Опечатка, встречающаяся один раз, тоже имеет высокий IDF.

## 5. TF-IDF и векторная модель документов

Можно взять вес `TF × IDF`. Чтобы многократное повторение слова не увеличивало вес строго линейно, используют sublinear TF:

\[
\operatorname{tf}'(t,d)=
\begin{cases}
1+\ln tf(t,d),&tf(t,d)>0;\\
0,&tf(t,d)=0.
\end{cases}
\]

Затем `w(t,d)=tf'(t,d)·idf(t)` и нормализация вектора по L2. Именно эти настройки явно включены в примере на scikit-learn. Формул TF-IDF несколько: всегда указывайте выбранный вариант. [2]

Каждая координата соответствует терму словаря. Если словарь содержит 100 000 термов, размерность тоже 100 000, но большинство координат документа равны нулю: это **разреженный вектор**.

Запрос переводится в тот же словарь и сравнивается с документами. Для L2-нормированных векторов скалярное произведение равно косинусному сходству.

**TF-IDF уже является векторным представлением.** В прикладных обсуждениях «векторным поиском» часто называют именно поиск по плотным нейросетевым эмбеддингам. Это терминологическое сокращение, а не отсутствие векторов у классического поиска.

### Python: TF-IDF

```python
from sklearn.feature_extraction.text import TfidfVectorizer

texts = ['возврат деньги карта', 'оплата карта карта', 'возврат товар']
v = TfidfVectorizer(norm='l2', smooth_idf=True, sublinear_tf=True)
x = v.fit_transform(texts)
q = v.transform(['возврат карта'])
scores = (x @ q.T).toarray().ravel()
print(sorted(enumerate(scores), key=lambda pair: -pair[1]))
```

`fit_transform` обучает словарь и статистику IDF на корпусе; `transform` применяет их к запросу. **Нельзя независимо обучать vectorizer на запросе:** координаты перестанут соответствовать корпусу.

Термы вне словаря не создают новых координат. Если все слова запроса неизвестны, получается нулевой вектор. В учебном классе результаты с нулевым score исключаются, чтобы не показывать произвольные документы как найденные. [3]

## 6. BM25: насыщение частоты и длина документа

BM25 тоже использует совпадающие термы и статистику корпуса, но отдельно учитывает насыщение TF и длину документа.

Используем следующую распространённую форму для коротких запросов:

\[
\operatorname{score}(q,d)=\sum_{t\in unique(q)}
\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right)
\frac{tf(t,d)(k_1+1)}{tf(t,d)+k_1\left(1-b+b\frac{|d|}{avgdl}\right)}.
\]

| Обозначение | Смысл |
|---|---|
| `N` | Число документов |
| `df(t)` | Число документов с термом |
| `tf(t,d)` | Число вхождений терма в документ |
| `|d|` | Длина документа в термах |
| `avgdl` | Средняя длина документов |
| `k1` | Управляет насыщением частоты |
| `b` | Управляет нормализацией по длине |

Повторения термов **запроса** здесь не учитываются; варианты BM25 могут обрабатывать их иначе. Наш код — учебная реализация выбранной формулы, не побитовая копия конкретного поискового движка. [4]

### Интуиция параметров

При длине документа, равной средней, и `k1=1.5` частотный множитель будет:

| TF | Множитель |
|---|---:|
| 1 | 1.000 |
| 2 | 1.429 |
| 10 | 2.174 |
| Стремится к бесконечности | Стремится к 2.500 |

Десять повторений не дают десятикратного преимущества. При увеличении `k1` насыщение становится менее быстрым. При `b=0` длина не влияет; при `b=1` нормализация по относительной длине максимальна в рамках этой формулы.

Длинный документ имеет больше шансов случайно содержать слово, поэтому длина учитывается. Но это не значит, что длинный документ автоматически нерелевантен.

## 7. BM25 на обратном индексе

В `lexical.py` класс `BM25` строит posting lists с частотами и длины документов. При запросе он перебирает только postings найденных термов и накапливает score по ID.

```python
from corpus import DOCS
from lexical import BM25, TfidfSearch

query = 'E17'
print(BM25(DOCS).search(query, k=5))
print(TfidfSearch(DOCS).search(query, k=5))
```

Оба метода должны поставить `d05` первым для `E17`. Полный запуск:

```bash
python lexical.py E17
python lexical.py 'возврат денег на карту'
```

У собственных scores BM25 в этом проекте **больше — лучше**. Их нельзя напрямую трактовать как вероятность и нельзя сравнивать с cosine либо использовать универсальный порог между разными корпусами.

## 8. Настоящий полнотекстовый индекс: SQLite FTS5

Чтобы показать поисковый движок, а не только формулу, в проекте есть `sqlite_search.py`. Он использует встроенный модуль Python `sqlite3`; сборка SQLite должна поддерживать FTS5.

Ключевая часть:

```python
import sqlite3

with sqlite3.connect(':memory:') as con:
    con.execute('CREATE VIRTUAL TABLE docs USING fts5(title, body)')
    con.executemany('INSERT INTO docs VALUES (?, ?)', [
        ('Ошибка E17', 'Банк отклонил оплату.'),
        ('Ошибка E71', 'Истёк срок сессии.'),
    ])
    result = con.execute(
        'SELECT title, bm25(docs) FROM docs '
        'WHERE docs MATCH ? ORDER BY bm25(docs) ASC',
        ('"E17"',),
    ).fetchall()
    print(result)
```

В SQLite FTS5 встроенная функция `bm25` возвращает оценку с противоположным направлением: **меньше — лучше**, поэтому сортировка `ASC`. Не переносите направление сортировки из другой реализации. [5]

`unicode61` умеет разбирать Unicode-текст, но не делает русскую лемматизацию. Поле `карта` не обязано совпадать с `карту`. В `sqlite_search.py` нет обещания идентичной токенизации с `lexical.py`.

Параметризованный SQL защищает структуру SQL-запроса, но строка `MATCH` всё равно имеет собственный язык операторов. В проекте пользовательские токены заключаются в кавычки и соединяются через OR. Это ограниченный режим поиска по словам, а не поддержка произвольного FTS-синтаксиса.

## 9. Где классический поиск ошибается

| Запрос | Возможная проблема |
|---|---|
| «не помню секретное слово» | В документе только «пароль» |
| «вернуть на карту» | Словоформы отличаются от текста |
| Русский вопрос, немецкий документ | Нет общих термов |
| «не принимается наличная оплата» | Совпадение слов не гарантирует учёт отрицания |
| «ошибка E17» | Общее слово «ошибка» вытягивает похожие коды |

Решения зависят от задачи: морфология, синонимы, поля с разными весами, phrase queries, точные фильтры, символьные n-граммы, векторный поиск и reranker. Нейросеть — один из инструментов, а не единственное исправление.

## Приложение: реализация BM25

Этот класс работает с записями `id`, `title`, `text` из `corpus.py`. Функции `tokenize` и `doc_text` определены в проекте. Импорты: `math`, `Counter`, `defaultdict`. Здесь явно видны построение обратного индекса и обход только совпавших postings.

```python
class BM25:
    def __init__(self, docs, k1=1.5, b=0.75):
        if k1 <= 0 or not 0 <= b <= 1:
            raise ValueError('Требуются k1 > 0 и 0 <= b <= 1')
        self.docs = list(docs)
        if len({d['id'] for d in self.docs}) != len(self.docs):
            raise ValueError('id должны быть уникальными')
        self.k1, self.b = k1, b
        self.lengths = {}
        self.postings = defaultdict(dict)
        for doc in self.docs:
            terms = tokenize(doc_text(doc))
            self.lengths[doc['id']] = len(terms)
            for term, count in Counter(terms).items():
                self.postings[term][doc['id']] = count
        self.n = len(self.docs)
        self.avgdl = sum(self.lengths.values()) / self.n if self.n else 0

    def search(self, query, k=5):
        if k <= 0 or not self.avgdl:
            return []
        scores = defaultdict(float)
        # Вариант для коротких запросов: повторения термов запроса не учитываем.
        for term in sorted(set(tokenize(query))):
            postings = self.postings.get(term, {})
            df = len(postings)
            if not df:
                continue
            idf = math.log(1 + (self.n - df + 0.5) / (df + 0.5))
            for doc_id, tf in postings.items():
                norm = 1 - self.b + self.b * self.lengths[doc_id] / self.avgdl
                scores[doc_id] += idf * tf * (self.k1 + 1) / (tf + self.k1 * norm)
        return sorted(scores.items(), key=lambda x: (-x[1], x[0]))[:k]

```
