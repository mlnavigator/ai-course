# Практикум: два MCP-сервера на Python

**Задание:** реализуйте MCP-сервер для SQLite и MCP-сервер для готового HTTP API. В каждом — четыре инструмента. Проверьте их Python-клиентом; при наличии агента подключите к нему оба сервера.

База `shop.db`, генератор данных, FastAPI-приложение и MCP-клиент даны в папке `starter`. Реализовать нужно `student_sqlite.py` и `student_api.py`. Готовых решений этих двух файлов в комплекте нет.

Ориентир — две пары по 90 минут при знакомстве с Python и SQL. LLM и ключи платных сервисов для обязательной части не нужны.

## 1. Подготовка

В папке `starter`:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python client.py example_basic.py calculate_total '{"price_kopecks":15000,"quantity":3}'
```

Ожидается `total_kopecks=45000`, `is_error=false`. Клиент запускает MCP-сервер сам. Команды рассчитаны на Bash; краткое описание Windows есть в теоретическом материале.

| Готовый файл | Назначение |
|---|---|
| `shop.db` | SQLite с данными магазина |
| `init_db.py` | Восстановление базы: `python init_db.py --reset` |
| `mock_api.py` | API службы доставки с данными в памяти |
| `client.py` | Получение списка tools и вызов выбранного инструмента |
| `example_basic.py` | Минимальный MCP-сервер |
| `example_sqlite.py` | Пример чтения одного клиента из SQLite |
| `example_http.py` | Пример обращения к `/health` мок-API |
| `student_sqlite.py`, `student_api.py` | Заготовки для самостоятельной работы |

## 2. Работа A: MCP над SQLite

### Данные

В базе четыре таблицы:

| Таблица | Поля |
|---|---|
| `customers` | `id`, `name`, `city` |
| `products` | `id`, `name`, `price_kopecks`, `stock` |
| `orders` | `id`, `customer_id`, `created_at`, `status` |
| `order_items` | `order_id`, `product_id`, `qty`, `unit_price_kopecks` |

`orders.customer_id` ссылается на клиента. `order_items` связывает заказ и товар. В базе 4 клиента, 4 товара, 7 заказов и 9 позиций заказов.

Все суммы хранятся в целых копейках. **Цена товара в каталоге и цена его продажи могут отличаться.** Сумма заказа считается по `order_items.unit_price_kopecks`, а не по `products.price_kopecks`.

Статусы заказов: `paid`, `pending`, `cancelled`, `refunded`. Для этой работы выручка — сумма позиций только заказов со статусом `paid`. Возвращённые заказы не входят; дополнительных вычитаний из суммы делать не нужно.

### Реализуйте четыре tools

Все результаты — словари, пригодные для JSON. Точные обязательные поля заданы ниже; дополнительные поля допустимы.

| Tool | Аргументы | Результат |
|---|---|---|
| `find_products` | `query: str`, `limit: int = 10` | `{"products": [...]}`: ID, название, цена, остаток |
| `get_order` | `order_id: int` | ID заказа, клиент, дата, статус, позиции и `total_kopecks` |
| `customer_orders` | `customer_id: int` | `{"customer_id": ..., "orders": [...]}`: ID, дата, статус, сумма каждого заказа |
| `sales_summary` | `date_from: str`, `date_to: str` | `paid_orders_count`, `revenue_kopecks` за включительный интервал дат |

Правила:

1. `find_products`: поиск подстроки в имени без учёта регистра для ASCII-названий этой базы. `%` и `_` во входе считаются обычными символами, не SQL-шаблонами. Пустая строка возвращает каталог с учётом `limit`. Сортировка — по ID; `limit` от 1 до 50.
2. `get_order`: неизвестный ID — ошибка инструмента. В позициях должны быть `product_id`, `name`, `qty`, `unit_price_kopecks`, `line_total_kopecks`.
3. `customer_orders`: заказы по ID по возрастанию. Существующий клиент без заказов — пустой список. Несуществующий клиент — ошибка. Для суммы каждого заказа учитываются все его позиции независимо от статуса.
4. `sales_summary`: даты в формате `YYYY-MM-DD`, реально существующие. Начало не позже конца. Пустой период — нулевые показатели, не ошибка. Число заказов — число заказов, а не строк после JOIN.

БД открывайте только для чтения, как в примере. Значения передавайте SQL-параметрами. Путь задавайте через `SHOP_DB`, по умолчанию — `shop.db` рядом с сервером. Не добавляйте в обязательную часть инструмент с произвольным SQL.

Пример формата заказа 101:

```json
{
  "order_id": 101,
  "customer": {"id": 1, "name": "Анна", "city": "Кострома"},
  "created_at": "2026-10-01",
  "status": "paid",
  "items": [
    {"product_id": 1, "name": "Keyboard", "qty": 1, "unit_price_kopecks": 200000, "line_total_kopecks": 200000},
    {"product_id": 2, "name": "Mouse", "qty": 2, "unit_price_kopecks": 80000, "line_total_kopecks": 160000}
  ],
  "total_kopecks": 360000
}
```

### Проверки работы A

| Вызов | Ожидаемый результат |
|---|---|
| `find_products("mouse")` | Один товар: ID 2, цена 80000, остаток 15 |
| `find_products("", 2)` | Первые два товара по ID |
| `find_products("%")` | Пустой список |
| `find_products("' OR 1=1 --")` | Пустой список, не весь каталог и не ошибка SQL |
| `find_products("mouse", 0)` | Ошибка ограничения limit |
| `get_order(101)` | 2 позиции, сумма 360000 |
| `get_order(104)` | Сумма 185000, учитывается цена продажи кабеля 35000 |
| `get_order(107)` | Сумма 75000, не текущая цена мыши 80000 |
| `get_order(999)` | Ошибка: заказ не найден |
| `customer_orders(1)` | Заказы 101, 103, 107; суммы 360000, 40000, 75000 |
| `customer_orders(4)` | Существующий клиент, пустой список |
| `customer_orders(999)` | Ошибка: клиент не найден |
| `sales_summary("2026-10-01", "2026-10-07")` | 4 оплаченных заказа, 2120000 копеек |
| `sales_summary("2026-10-04", "2026-10-07")` | 2 оплаченных заказа, 260000 копеек |
| `sales_summary("2026-11-01", "2026-11-02")` | Оба показателя равны 0 |
| Несуществующая дата или обратный интервал | Ошибка входных данных |

Запуск:

```bash
python client.py student_sqlite.py
python client.py student_sqlite.py get_order '{"order_id":101}'
python client.py student_sqlite.py sales_summary '{"date_from":"2026-10-01","date_to":"2026-10-07"}'
```

Пустой список tools означает, что функции ещё не зарегистрированы. При неизвестном tool проверьте имя и декоратор.

## 3. Работа B: MCP над FastAPI

### Запуск готового API

В отдельном терминале с тем же окружением:

```bash
python -m uvicorn mock_api:app --host 127.0.0.1 --port 8000
```

Откройте `http://127.0.0.1:8000/docs`. Изучите параметры, JSON запросов и ответы. Пример MCP-вызова к уже запущенному API:

```bash
python client.py example_http.py delivery_health
```

Данные доставок хранятся в памяти FastAPI-процесса. При перезапуске они возвращаются к исходному состоянию. Используйте один worker. SQLite и API — независимые источники; совпадающий `order_id` позволяет сопоставлять данные.

### Готовые HTTP-операции

| HTTP API | Назначение |
|---|---|
| `GET /shipments` | Все доставки; необязательный query-параметр `status` |
| `GET /shipments/{order_id}` | Доставка конкретного заказа; 404, если её нет |
| `POST /shipping/quote` | Расчёт цены по JSON `weight_grams`, `zone` |
| `POST /shipments/{order_id}/reschedule` | Изменение даты по JSON `planned_date` |

Статусы доставки: `created`, `in_transit`, `delivered`. Это **не** статусы оплаты из SQLite.

Тариф: для `local` база 15000 копеек, для `regional` — 30000. Добавляется 5000 копеек за каждый начатый килограмм. Вес — от 1 до 30000 граммов.

Перенос разрешён для недоставленных заказов. Дата должна быть не раньше **2026-10-10** — это фиксированное правило учебного сценария, оно не зависит от текущей даты компьютера. Доставленный заказ даёт HTTP 409; недопустимые параметры — HTTP 422.

### Реализуйте четыре tools

| MCP tool | Сигнатура |
|---|---|
| `list_deliveries` | `status: str \| None = None` |
| `get_delivery` | `order_id: int` |
| `quote_delivery` | `weight_grams: int, zone: str` |
| `reschedule_delivery` | `order_id: int, planned_date: str` |

Для статусов и зон можно использовать `Literal`, чтобы перечисление допустимых значений попало в схему tool. Результат успешного вызова — JSON исходного API без потери полей.

Требования:

1. API вызывается **по HTTP через `httpx`**. Нельзя импортировать `SHIPMENTS` или функции из `mock_api.py`.
2. Базовый URL берётся из `DELIVERY_API_URL`, по умолчанию `http://127.0.0.1:8000`.
3. У запросов задан таймаут. HTTP 404, 409, 422 превращаются в понятные ошибки инструмента; код HTTP и причина должны быть различимы.
4. Недоступность API не маскируется под пустой список или успешное изменение.
5. `reschedule_delivery` в описании явно сообщает, что изменяет дату. После него результат проверяется отдельным `get_delivery`.
6. Формулу тарифа и правила переноса не копируйте в MCP-сервер: их выполняет API. Задача обёртки — корректно вызвать операцию и передать результат.

Не нужно делать общий tool `request(method, url, body)`. В этой работе цель — четыре предметных инструмента с понятными аргументами.

### Проверки работы B

| Вызов | Ожидаемый результат |
|---|---|
| `list_deliveries()` | 4 доставки: 101, 102, 104, 107 |
| `list_deliveries("created")` | Заказы 104 и 107 |
| `get_delivery(102)` | `in_transit`, Ярославль, дата 2026-10-11 |
| `get_delivery(999)` | Ошибка с причиной «не найдено», HTTP 404 |
| `quote_delivery(1500, "local")` | 25000 копеек, RUB |
| `quote_delivery(1000, "regional")` | 35000 копеек, RUB |
| `quote_delivery(1001, "regional")` | 40000 копеек, RUB |
| Вес 0 или неизвестная зона | Ошибка валидации; не успешный тариф |
| `reschedule_delivery(104, "2026-10-15")` | Новая дата 2026-10-15; следующий `get_delivery(104)` подтверждает её |
| `reschedule_delivery(101, "2026-10-15")` | Ошибка HTTP 409: заказ уже доставлен |
| Перенос 104 на 2026-10-09 | Ошибка HTTP 422; прежняя дата не изменилась |
| Остановить FastAPI и вызвать `get_delivery(102)` | Ошибка недоступности API |

Если ограничения веса и зоны проверены схемой MCP до HTTP-запроса, допустима ошибка валидации MCP. Не нужно утверждать, что в этом случае API вернул HTTP 422: до него запрос мог не дойти.

Запуск из второго терминала:

```bash
python client.py student_api.py
python client.py student_api.py get_delivery '{"order_id":102}'
python client.py student_api.py quote_delivery '{"weight_grams":1500,"zone":"local"}'
```

## 4. Проверка без агента и с агентом

Обязательная часть — показать реальные вызовы через `client.py` или собственный Python MCP-клиент. Прямой вызов импортированной функции полезен для отладки, но не доказывает, что MCP-интерфейс работает.

Для автоматизации используйте `Client` из теоретического материала. После `call_tool` проверяйте `is_error`, затем данные `structured_content`. Возвращайте из обработчиков `dict[str, Any]`, как в примерах; `Any` импортируется из `typing`. Можно вместо этого описать результат Pydantic-моделью.

При наличии агента подключите оба сервера и дайте задачи:

1. «Что заказала Анна, клиент 1? Для каждого заказа укажи сумму и статус оплаты».
2. «Какая выручка по оплаченным заказам с 1 по 7 октября 2026 года?» — ожидается 21200 рублей.
3. «Найди ещё не доставленные оплаченные заказы Анны» — заказ 107; 101 доставлен, 103 отменён и не должен попадать в результат.
4. «Перенеси доставку заказа 104 на 15 октября 2026 года и проверь новую дату».

В третьей задаче агент соединяет сведения из двух систем по `order_id`. Не заставляйте один MCP-сервер обращаться к другому: для этого задания координация остаётся у клиента/агента.

Сохраните использованные tools, аргументы и результаты. Правильный текстовый ответ без фактических вызовов не подтверждает работу интеграции. Если агента нет, выполните ту же последовательность явно через Python-клиент и укажите этот режим.

## 6. Оценивание

| Критерий | Баллы |
|---|---:|
| SQLite: четыре инструмента, корректные JOIN, суммы, даты и пустые результаты | 35 |
| HTTP: четыре обёртки, реальные запросы, обработка ошибок и подтверждённое изменение | 35 |
| MCP: инструменты обнаруживаются клиентом, схемы и описания соответствуют функциям | 15 |
| Воспроизводимые проверки и задача с данными двух систем | 15 |
| **Всего** | **100** |

На защите преподаватель меняет цену продажи в позиции заказа или данные мок-API и повторяет вызов. Сервер должен читать актуальные данные, а не возвращать зашитые контрольные ответы.
