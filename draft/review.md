# Разбор драфта курса «Использование ИИ в бизнесе и разработке ПО»

Аудитория: студенты 3–4 курса ИТ-специальностей + практикующие ИТ-специалисты, входящие в тему.

---

## Что в драфте хорошо

- **Широта охвата**: от основ LLM до саморазвёртывания моделей — редкая полнота для одного курса.
- **Практическая ориентированность**: конкретные инструменты (ClaudeCode, Cursor, OpenCode, GigaCode), MCP, OpenRouter — не абстрактная теория.
- **Раздел безопасности** присутствует — это часто забывают, а для ИТ-аудитории критично.
- **Spec-driven development** в связке с TDD/DDD/SOLID — правильный акцент на том, что ИИ меняет не сам код, а процесс его создания.

---

## Ключевые пробелы (рекомендуется добавить)

### 1. Промпт-инжиниринг и контекст-инжиниринг — фундамент полностью отсутствует

Сейчас курс прыгает от «что такое LLM» сразу к агентам. Между ними — пропасть.

**Что добавить:**
- Базовые техники промптинга: few-shot, chain-of-thought, role-based prompting
- Структурированный вывод: JSON mode, function calling vs tool calling — различия
- Управление контекстным окном: что помещается, что обрезается, стратегии сжатия
- Контекст-инжиниринг: как собирать релевантный контекст для задачи
- Системные промпты vs пользовательские, thread/context management
- Шаблонизация промптов (prompt templates, Jinja2 для промптов)

**Почему важно:** без этого студенты не поймут, *почему* агенты работают или не работают. Это базис.

### 2. Эмбеддинги и векторные БД — скрыты за RAG

RAG упомянут, но технология под ним — нет. Для ИТ-аудитории это нужно раскрыть.

**Что добавить:**
- Что такое эмбеддинги, размерности, косинусное сходство
- Векторные БД: практический обзор (Qdrant, Chroma, pgvector, Pinecone)
- Chunking стратегия, перекрытия, метаданные
- Reranking, hybrid search (BM25 + векторы)
- Метрики качества поиска (recall@k, MRR)

### 3. Оценка качества ИИ-систем (evals) — нет ни слова

**Что добавить:**
- Почему нельзя доверять «тесту на глаз»
- Метрики: BLEU/ROUGE (пределы), LLM-as-judge, human eval
- Создание наборов тестов для промптов/агентов
- A/B тестирование промптов
- Monitoring в продакшене: drift detection, quality dashboards

**Почему важно:** без evals нельзя доказать, что изменение промпта/модели — улучшение, а не регрессия.

### 4. Файн-тюнинг — отсутствует при наличии раздела развёртывания

Развёртывание есть, а адаптации модели под задачу — нет.

**Что добавить (хотя бы обзорно):**
- SFT (Supervised Fine-Tuning), когда нужен
- LoRA / QLoRA — почему это практический стандарт
- Разница fine-tuning vs RAG vs prompt engineering — когда что выбирать
- DPO / RLHF — концептуально, без глубокой математики

### 5. Этика, право и комплаенс — нет

Для ИТ-специалистов в бизнесе это не «философия», а практические риски.

**Что добавить:**
- Авторское право и тренировочные данные: текущее состояние дел
- Использование выводов ИИ в коммерческом продукте — юридические риски
- GDPR / 152-ФЗ: персональные данные в промптах и логах
- Утечка данных через промпты (Samsung case и аналогичные)
- Политика использования корпоративных данных в облачных ИИ-сервисах

### 6. Практический выбор модели и экономика

**Что добавить:**
- Сравнение моделей по задачам: GPT-4o vs Claude vs Gemini vs open-source (Llama, Qwen)
- Токен-экономика: стоимость, rate limits, latency vs quality tradeoff
- Локальная модель vs API: когда что оправдано
- Кеширование ответов, семантический кеш
- Стриминг ответов и UX

### 7. Мульти-агентные системы

Сейчас — один агент. Реальные продакшен-системы часто мультагентны.

**Что добавить:**
- Паттерны: router, supervisor, peer-to-peer агенты
- Координация и коммуникация между агентами
- Когда мультиагентность оправдана, а когда — лишняя сложность
- Human-in-the-loop: где нужен контроль человека

## Структурные замечания

### Раздел «Безопасность» перегружен и смешивает два курса

Сейчас там одновременно: ИИ-специфичные угрозы (галлюцинации, промпт-инъекции, RAG-инъекции) **и** классическая безопасность ПО (OWASP 10, CWE/CVE, SSL).

**Рекомендация:** чётко разделить:
- **«ИИ-безопасность»**: галлюцинации, промпт-инъекция, отравление данных, байесы LLM, LLM OWASP 10, guardrails
- **«ИИ для аудита безопасности»**: как использовать агентов для поиска CWE/CVE, аудита кода, анализа 0-day — это уже *применение*, а не теория

Это два разных навыка: защищать ИИ-систему vs использовать ИИ для защиты обычного ПО.

### Раздел разработки слишком традиционный

SOLID, MVC, Clean Code — студенты 3–4 курса это, скорее всего, уже проходили. Риск: «зачем нам это снова?»

**Рекомендация:** переформулировать через призму ИИ:
- Не «что такое SOLID», а «как SOLID помогает ИИ-агенту вносить изменения без поломки»
- Не «что такое TDD», а «почему тесты критичны именно при ИИ-генерации кода — ИИ пишет быстро, но без тестов регрессии неизбежны»
- Спецификация как *договор* между человеком и ИИ-агентом — это сильный фрейм

### Нет явного формата практики / проектов

Для ИТ-студентов критично: теория без рук не сядет.

**Рекомендация:** добавить блок «Практические проекты»:
- Мини-проект: MCP-сервер для реальной задачи
- Мини-проект: RAG по собственной документации
- Финальный проект: агент для реальной рабочей задачи студента

## Чего нет, но, возможно, не нужно (чтобы не перегружать)

- Глубокая теория трансформеров (attention, positional encoding) — для этой аудитории избыточна
- Обучение моделей с нуля (pretraining) — нецелевая аудитория
- Reinforcement Learning в деталях — слишком глубоко

Эти темы стоит упомянуть как «что дальше», но не разбирать.

## Резюме

Драфт — крепкая база, но сейчас это **скелет без connective tissue**. Главные пробелы:

1. **Промпт- и контекст-инжиниринг** — фундамент, без которого агенты — чёрный ящик
2. **Эмбеддинги/векторные БД** — раскрыть под RAG
3. **Evals** — как измерять качество
4. **Этика/право** — практические риски для бизнеса
5. **Экономика моделей** — выбор и стоимость

Если приоритизировать: пункты 1 и 2 — обязательно, остальные — по доступному времени.

Структурно: раздел безопасности разделить на два, раздел разработки переформулировать через призму ИИ, добавить практические проекты.
